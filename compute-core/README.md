# Obrato · compute-core (TypeScript-прототип)

Детерминированный движок прораба. **Та половина приложения, от которой зависит,
работает продукт или нет.** UI её только отображает.

```
модель ввода → нормы расхода → количества → округление до упаковок → лист закупок по этапам
(размеры + работы)  (число+допущения)              (с коэф. отхода)         (+ SVG план пола)
```

## ⚠️ Статус: референс-прототип, НЕ спецификация ядра

Продуктовое ядро пишется на **Rust** (`crates/compute-core`, гл.03/09, решение D3);
TS-типы продукта генерятся ИЗ Rust (tsify). Этот модуль — ранний прототип
(2026-05-29): полезен как референс пайплайна, golden-фикстуры и каталог-валидация,
но **контракт у него устаревший**:

- выход — **точечная оценка** (`rawQuantity: number`), а не `NormValue`-диапазон
  с confidence (D7, гл.05 §3/§8);
- **формулы гл.07 не реализованы** (плоское `perUnit × площадь`) — спецификация
  формул = **гл.07**, не `norms-table.ts`;
- план пола отдаётся **SVG-строкой** — вопреки D2 («ядро отдаёт данные»).

Источник истины контракта ядра — **гл.05 §8 + гл.07 + гл.09 §2**. Миграционный план
прототипа — гл.09 §5 «Судьба TS-прототипа».

## Архитектурный инвариант

`compute-core` — **отдельный чистый модуль**: чистые функции, ноль зависимостей
от UI/DOM/браузера. Один и тот же модуль крутится:
- в **PWA** — клиентский расчёт (в Web Worker, вне UI-потока);
- **headless** — генерация листа/PDF для пилота (concierge).

Зачем так: когда лист закупок соврёт в количествах (а он соврёт — см. ниже), баг
пинится в юнит-тестах движка за минуту, а не ищется по всему быстро-сгенерённому
аппу. Держи эту границу чистой даже когда строишь UI рядом.

## Запуск

Нужен **Node ≥ 22.18** (нативный стриппинг TypeScript — тесты бегут без установки
зависимостей):

```bash
node --test          # юнит-тесты (17 шт.: пайплайн + каталог)
npm install          # только для полного typecheck
npm run typecheck    # tsc --noEmit
```

## ⚠️ Главное: нормы — это Risk #1, и они НЕ валидированы

Коэффициенты в `norms-table.ts` — стартовые заглушки, выровненные с seed-значениями
гл.07. Часть реальных входов (зубец шпателя, паттерн раскладки, ровность основания
под стяжку, заход гидроизоляции) в модели ввода Д×Ш×В **отсутствует** — они зашиты
как допущения и едут в каждый результат (`assumptions.notes`), чтобы при сверке было
видно ГДЕ движок соврал.

**Задача первого пилота — не угадать эти числа здесь, а узнать настоящие**: см.
бумажный M0-prep без кода — `docs/design/12-m0-prep-worksheet.md` (чеклист +
CSV-шаблон) и `docs/design/11-pilot-plan.md` (слайсы −1…2, метрика D5).

## Что сознательно НЕ здесь (фаза 2)

Solver балансировки подрезки плитки, разводка электрики трассами, непрямоугольная
геометрия, отслеживание отклонений по ходу стройки (drift), Bluetooth-дальномер.
